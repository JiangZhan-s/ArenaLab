# 量化实验与面试证据

## 工作量不等于技术成果

课程共 15 Lab。每 Lab 固定四个任务，按设计/实现/反例/解释四项交付，共 60 个任务单位；不是60个相同工时单位。建议每次完成一个可验证任务。

初始规划预算（非承诺）：00～03 约 25～45 小时；04～08 约 55～95 小时；09～11 约 30～50 小时；12～14 约 45～80 小时。总计155～270小时，包括读资料、实验、排障和答辩，不按 Codex 输出代码速度估算。真实 UE 编译/接入另留15～40小时以上，环境差异可能显著增加时间。

每次记录 actual_minutes、任务、失败原因和剩余学习债；完成两 Lab 后用实际数据重估。进度分别记 task_done、gate_pass、explanation_pass；不把“生成了文件”当成三者都完成。

## 五个有业务动机的对照实验

| 问题 | 基线 → 候选 | 固定条件 | 指标与解释 |
|---|---|---|---|
| 一个慢玩家能否拖慢别的局？ | 同步广播 → 有界独立发送队列 | 相同房间数、活跃率、慢读比例 | 健康房间 P99、队列峰值、拒绝/断连数、RSS；保留丢弃语义 |
| 小场景需要 delta 吗？ | 全量快照 → delta+定期基线 | 相同状态、输入、RTT 与重连时刻 | 字节/秒/玩家、序列化 CPU、重连流量与正确性；小状态可能全量更好 |
| 什么保证值得持久化成本？ | abort/no-score → 回合制逐行动持久化恢复 | 相同输入与故障窗口 | ACK P99、SQL/s、恢复时间、已确认丢失数；禁止拿实时易失 ACK 比 durable ACK 宣称优化 |
| 房间容量卡在哪？ | 每房间 goroutine → 经测量有必要再做共享调度 | idle/active/slow 三种负载分别测 | goroutine/room、RSS/room、tick 执行与落后、GC；不默认复杂调度更优 |
| 分配速度与资源占用怎么取舍？ | 按需启动 DS → 预热 ready 池 | 同 build/region、同到达率 | 分配 P50/P99、无容量比例、空闲 RSS、冷启动时间、泄漏分配数 |

每项先写假设，执行 A/B/A 或交错顺序，至少各3次。保存硬件、CPU限额、Go/DB/OS版本、SHA、参数、随机种子和原始数据。报告每次值与中位数/范围，不只挑最好一次。

## 负载与计算规范

先预热15秒，再测30秒以上；30秒只是快速 Gate，最终容量实验建议每档120秒并观察稳定性。使用开放到达率调度，延迟起点是计划发送时间而非真正写 socket 时间，避免客户端排队被隐藏。记录 offered/completed/rejected/timeout/error，负载机 CPU 一并保存。

不同 ACK 语义、连接人数与活跃人数必须分开；不把1000条空闲连接写成1000个并发对战请求。失败和超时必须进入原始数据，不能删掉失败后只展示漂亮的 P99。

已有可运行汇总工具：`go run ./cmd/measure artifacts/raw/run.json`。输入格式：
工具烟雾测试可运行 `go run ./cmd/measure fixtures/measurement-example.json`；该文件明确为合成样本，不是项目性能。

```json
{
  "commit": "真实完整SHA",
  "environment": "CPU/内存/OS/Go/数据库/进程限额与配置路径",
  "variant": "baseline",
  "seed": 451,
  "window_ms": 30000,
  "expected_requests": 2,
  "samples": [
    {"id":"1","scheduled_ms":0,"finished_ms":20,"outcome":"success"},
    {"id":"2","scheduled_ms":5,"finished_ms":1005,"outcome":"timeout"}
  ]
}
```

上例是格式示例，不是成绩。真实 expected_requests 必须来自预定负载计划，不能事后等于剩下的成功请求数。工具使用 nearest-rank 分位数，包含失败，拒绝缺失/重复样本；吞吐分母包含尾部排空时间。工具不证明采样真实，必须结合客户端日志与服务器计数核对。

容量结论形如：“在[配置]、[场景/到达率]下，持续[时长]，成功率[X]、P99[Y]、tick落后[Z]。”目标阈值先登记，再找最后一个合格档位。Gate09 的100房间/200请求每秒和250ms是本地教学预算，不是大厂生产 SLA。

## 面试如何回答“比别的项目好在哪里”

不要比较无法核实的别人的项目。比较自己的基线与演进：

> 我选的业务是玩家进入独立比赛服、完成对局并可靠结算。除了可玩闭环，我重点验证了慢连接隔离、故障下的承诺和 DS 结果信任边界。相比第一版，[方案]在[相同条件]下将[指标]从[A]改为[B]，代价是[C]。我保留了复现脚本和失败案例。

未测量前保持 A/B 空白。简历禁止写虚构日活、线上事故或“生产级”；应写“可复现的故障注入/容量实验”。

每个专题准备五问：为什么真有此需求？最简单方案是什么？哪次实验推翻了直觉？故障窗口在哪里？需求变成10人/60Hz/跨地域会改变哪些保证？

重点追问：

1. 为什么实时输入不逐帧落库，结果却必须可靠？丢失 ACK 后怎么区分？
2. 服务端权威能防哪些作弊，为什么不能防被攻破的 DS？
3. 快照更旧但客户端更快时，校正为何不能简单叠加位置？
4. 一次性票据与重连是否冲突？谁有权发新票据？
5. allocate 超时但实例已分配，怎样避免两场比赛？
6. ready 进程崩溃、drain 中断、结果与过期竞态，哪一个事实决定计分？
7. 压测客户端慢了为何可能让服务端 P99 看起来变好？
8. Go ds-sim 验证了什么，真实 UE 还缺什么？

答辩必须指向具体代码、SQL、原始实验和限制；仅背此文不算通过。
